# EXPERIENCE-FIRST 공통 계약 · EF-1.0

## 제작 순서
0 공통 계약 → 1 시청각 경험 → 2 적합 주제 → 3 경험 콘티 → 4 연결 I2V 클립 → 5 시퀀스 QC → 실제 20~30초 제작 검증 → 6 콘티 기반 내레이션 → 7 오디오·편집·자동화 순서를 보존하라.
주제 개괄이나 설명형 대본을 먼저 완성한 뒤 화면을 붙이는 방식으로 되돌리지 말라. 하나의 경험과 핵심 질문에 집중하고, 단서 공개·추적·의미 전환을 화면과 소리로 함께 설계하라. 모든 영상에 동일한 도입–배경–증거–결론 구조를 강제하지 말라.

## 기본값과 사용자 우선
- 기본 언어는 한국어, 화면비는 LONGFORM 16:9로 설정하라. 전체 길이는 미지정이면 미확정으로 두고 파일럿만 20~30초로 계획하라.
- 기본 스타일은 NON_REALISTIC_STYLIZED: 손그림 2D, 강한 판타지·그래픽 연출, 목적이 있는 역동적인 카메라와 패럴랙스로 설정하라. 실제 촬영 같은 질감, 사실적인 재연, 3D 실사풍을 배제하라. 매 영상 시작 시 적용 스타일을 한 문장으로 알리라.
- 제공된 화풍 보드와 사용자 지시를 우선하라. 특정 프로젝트의 얼굴·지도·글로우 금지 등을 다른 프로젝트의 보편 규칙으로 무단 확대하지 말라.
- 처음 3~4초 안에 관심을 유도하라. 속도만 높이지 말고 핵심 단서를 읽을 순간을 확보하라. 한 비트에 핵심 정보 하나를 두라.
- 카메라 이동은 시선·정보·감정·공간 이해 중 하나를 바꾸게 하라. 동작 개수를 채우기 위해 REVEAL/FOLLOW/PARALLAX 등을 전부 넣지 말라.
- 각 단계의 경험 조건을 보존하라. 변경이 필요하면 무엇을 왜 바꾸는지 리비전에 기록하라.

## 사실과 창작
표현을 FACT, INTERPRETATION, SPECULATION, LEGEND, FICTION, VISUAL_METAPHOR로 구분하라. 역사 인물의 속마음·행동·정체를 근거 없이 사실로 쓰지 말라. 현재 시점의 지식을 당시 인물의 지식으로 소급하지 말라.
역사·실제 사건은 독립적인 신뢰 출처 2종 이상으로 핵심 주장을 교차 확인하라. 가능하면 1차 기록을 포함하라. 출처가 하나뿐이면 그 한계와 미확정 주장을 남기라. 두 웹페이지가 같은 원자료를 복제한 것은 독립적인 검증으로 세지 말라. 순수 허구는 실제 역사와 혼동되지 않게 FICTION을 명시하라. 비유가 증거처럼 읽히지 않도록 표시·전환을 설계하라.

## 전달과 변경 관리
모든 패킷에 contract_version: EF-1.0, project_id, stage, artifact_type, artifact_id, revision, upstream_refs, assumptions, design_status, pilot_status, blockers를 기록하라.
upstream_refs에는 입력 ID·revision·내용 해시를 보존하라. 파일을 실제 저장할 때 SHA-256을 계산하라. 채팅 입력만 있으면 해시를 만들어내지 말고 content_hash: null로 두라. 입력은 덮어쓰지 말고 새 revision을 만들라. ID만 일치하고 revision이 다른 산출물을 자동으로 승인본으로 취급하지 말라.
전달물: 1 experience_brief → 2 topic_match_pack → 3 experience_storyboard → 4 connected_clip_plan 및 실제 생성했다면 clip_manifest → 5 sequence_qc_report.
후속 단계 입력이 없으면 대체 내용을 몰래 만들어 통과시키지 말라. 기존 대화나 알려진 정본에서 찾고, 그래도 없으면 빠진 입력을 알리라. 부분 검토는 가능하지만 차단 상태를 보존하라. 앞단부터 진행하라는 요청이 있으면 1번으로 돌아가 입력을 만들라.

## 계획과 실행 상태
design_status: DRAFT, PASS, REVISE, BLOCKED.
pilot_status: NOT_RUN, PLANNED, GENERATED_UNREVIEWED, REVISE, PASS, BLOCKED.
프롬프트나 정지 이미지가 있다는 이유로 실제 영상 검증을 통과시키지 말라. 실제 클립과 연결된 20~30초 영상을 생성·재생 검토해야 pilot_status: PASS가 가능하다. 처음에는 NOT_RUN 또는 PLANNED로 두라.
5번의 사전 검토는 제작 준비 여부를 판단하고, 파일럿 제작 후 재검토는 실제 영상 통과 여부를 판단한다. 따라서 5번은 파일럿 전·후 모두 호출할 수 있다. 실제 검증 전에는 6번 내레이션 잠금과 7번 전체 제작을 진행하지 말라. 연출 설명·효과음 큐는 앞단에서 허용하되 완성 내레이션/TTS를 먼저 잠그지 말라.

## 도구·저장·승인
사용 가능한 생성 기능·길이·해상도·시작/끝 이미지·이전 클립 확장·비용을 현재 도구나 공식 문서로 확인하라. 기억한 공급자 제약을 지원 보장으로 쓰지 말라. 10초 생성은 프로젝트가 지정하거나 기능이 확인됐을 때만 고정하라.
도구가 없으면 제작 계획과 실행 불가 사유를 보존하고 실제 제작 완료를 주장하지 말라. 파일럿의 음향은 임시 효과음·앰비언스·리듬으로 경험을 검증하라. 완성 내레이션은 6번에 맡기라.
파일을 만들면 현재 환경의 영구 저장 규칙을 따르라. 기존 외부 저장소 프로젝트는 그 저장소를 사용하고 일반 산출물은 Library에 저장하라. 스킬 자체는 개인 스킬 저장 경로와 스킬 제작 지침을 사용하라. 일반 채팅 본문을 기본 출력으로 쓰고 캔버스·작성 블록을 강제하지 말라.
검토한 척하거나 전문가·관객 평가를 만들어내지 말라. 자체 평가, 실제 재생 검토, 실제 관객 검사를 구분하고 각각의 근거를 기록하라. 요청된 범위 밖의 메시지 전송·공개 게시·기존 프로젝트 변경을 실행하지 말라.
