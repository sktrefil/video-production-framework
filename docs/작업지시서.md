## EDB-01 — Roman IX 현재 DB/미디어 상태 진단 고정

### 목적

현재 Roman IX 프로젝트의 실제 DB 상태를 코드 수정 전에 확정한다.

### 확인 항목

- [ ] 프로젝트 ID가 `pilot_short_roman_ix`인지 확인
- [ ] `project.db` 위치 확인
- [ ] MediaArtifact 목록 확인
- [ ] 실제 영상 10개가 MediaArtifact로 등록되어 있는지 확인
- [ ] 각 MediaArtifact의 `AVAILABLE`, duration, relativePath 확인
- [ ] QC 결과가 PASS 또는 허용된 TRIM_PASS인지 확인
- [ ] 현재 MediaBinding 목록 확인
- [ ] `MediaBindingPipeline.buildEditorHandoff(projectId)` 결과 확인
- [ ] handoff `READY/PARTIAL/BLOCKED`와 blocker 전체 기록
- [ ] 최신 EditorContentPlan 존재 여부와 planStatus 확인
- [ ] 최신 TimelineAssemblyRecord 존재 여부 확인
- [ ] materialize가 현재 `ASSEMBLY_NOT_FOUND`를 내는지 재현

### 산출물

진단 로그 또는 테스트 출력으로 아래 값을 남긴다.

```text
projectId
mediaArtifactCount
bindingCount
handoffStatus
handoffBlockers
contentPlanRevision
contentPlanStatus
assemblyRevision
assemblyStatus
assemblyStale
```

### 완료 조건

원인이 단순 파일 부재가 아니라 canonical binding/content/assembly 중 어느 단계의 부재인지 DB 기준으로 확정되어야 한다.

- `packages/editor-timeline`
- `packages/media-binding`
- `packages/storage`

### 구현 구조

```ts
const repo = new SqliteEditorTimelineRepository(projectDbPath);

const handoff = new MediaBindingPipeline(
  repo,
  repo,

  ids

  repo,
  handoff,
  clock,
  ids,
  repo
);

const result = await pipeline.assembleProject({
  projectId,
  projectName,
  profile
```

# Codex 작업 규칙

Codex 또는 다른 구현 에이전트는 다음 규칙을 지킨다.

1. 먼저 `docs/ROMAN_IX_EDITOR_ASSEMBLY_DB_DESIGN.md`를 읽는다.
2. 본 `작업지시서.md`를 EDB-01부터 순서대로 수행한다.
3. 기존 WF-13~16 domain/service/repository를 최대한 재사용한다.
4. 새 병렬 timeline architecture를 만들지 않는다.
5. 직접 SQL INSERT로 assembly를 생성하지 않는다.
6. 테스트를 통과시키기 위해 fixture media를 Roman IX production project에 넣지 않는다.
7. 각 EDB 작업 완료 시 변경 파일, 테스트 결과, blocker를 기록한다.
8. 실패한 gate가 있으면 다음 단계에서 숨기거나 우회하지 않는다.
9. Roman IX만 동작하는 하드코딩보다 generic production path를 우선한다.
10. 최종 완료 보고에는 반드시 assembly revision, handoff status, content plan revision/status, materialize 결과, Studio mode, render 결과를 포함한다.
